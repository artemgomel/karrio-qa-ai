# Дизайн тест-кейсов

## Шаги

1. Возьми требования (и ответы на вопросы, если они есть).
2. Примени техники: классы эквивалентности, граничные значения, таблица решений,
   переходы состояний. Для каждого числового ограничения — минимум три значения: на границе, внутри, за границей.
3. Каждому кейсу назначь:
   - **Приоритет:** P1 — деньги/потеря посылки/блокер, P2 — основной функционал, P3 — косметика.
   - **Уровень:** `API` — бизнес-правила и расчёты; `UI` — только то, что видит пользователь
     (отображение, навигация, сверка UI с API); `Manual` — исследовательское, визуал, один раз.
   Правило: если кейс можно проверить на API — он идёт на API. UI-тестов минимум.
4. Отметь, какие кейсы уже покрыты тестами в `tests/` (поищи по коду).

## Формат

Таблица Markdown:
`ID | Требование | Название | Шаги (кратко) | Ожидаемый результат | Приоритет | Уровень | Покрыт?`

После таблицы — 3–5 строк: что автоматизировать первым и почему.

## Правила
- Ожидаемый результат — конкретный и проверяемый (число, статус, текст).
- Не дублируй кейсы, отличающиеся только данными: объединяй в параметризованный.
