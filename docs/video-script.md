## 3. Анализ требований — 3 мин

## 4. Тест-кейсы и риски — 3 мин
> Используй скилл qa-test-design для этих требований. Отметь, что уже покрыто в tests/.

- Показать таблицу: приоритеты, уровни API/UI/Manual.
- Ключевая мысль: **бизнес-правила — на API, в UI только то, что видит пользователь.** Поэтому UI-тестов мало, и они стабильные.
- Риски: неверная цена (деньги клиента), посылка тяжелее лимита, тихий пустой результат.

## 5. Автоматизация — 4–5 мин
Показать архитектуру коротко: `src/fixtures.ts` (данные через API), page objects, `data.setup.ts` (свой перевозчик без реальных аккаунтов).

Живой пример: попросить AI добавить тест.
> Используй скилл qa-playwright-test: добавь UI-тест, что в карточке отправления отображается сервис Demo Standard. Посмотри страницу через Playwright MCP.

- Показать, как AI открывает страницу через MCP и выбирает локатор.
- **Ревью:** что поправил в сгенерированном коде (локатор, ожидание, захардкоженное значение).
- Запустить: `npm run test:api`, затем `npm run test:ui`. Показать HTML-отчёт и trace.

Показать находку **KQA-1**: тест `empty result explains why no rate is available` помечен `test.fail()` с аннотацией issue — известный баг виден в отчёте, но не ломает пайплайн.

- `.github/workflows/e2e.yml`: Karrio поднимается в Docker, проекты api / ui-desktop / ui-mobile идут параллельно, ночной регресс по расписанию, артефакты с trace и логами API.
- Разбор падений с AI: сломать один локатор, запустить, затем
> Используй скилл qa-failure-triage по test-results/results.json.
- Показать: AI разделил «баг продукта» и «баг теста», для бага подготовил черновик репорта.

## 7. AI в ежедневном процессе и работа с разработкой — 2 мин
- Ревью требований до спринта → вопросы аналитику сразу.
- Тест-кейсы и автотесты в одном PR с фичей, AI помогает написать, человек ревьюит.
- Разбор красного CI за минуты вместо ручного копания в логах.
- Мой опыт: в B2Broker и Nielsen делал скиллы для мануальных QA — генерация кейсов и тест-данных, меньше рутины.

## 8. Как думаю о качестве — 1 мин
- AI ошибается → всё ревьюится, решения за мной.
- Смотрю не на количество тест-кейсов, а на: время регресса, долю флейков, баги, дошедшие до прода.
- Цель — меньше ручной рутины и раньше найденные проблемы, а не больше тестов.
